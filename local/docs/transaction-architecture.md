# Transaction architecture

Hermes owns conversation and orchestration. ErrandOS owns typed provider access, durable state, immutable SHA-256 proposals, expiration, ownership, approval verification, idempotency, final-action dispatch, receipts, and reconciliation.

Blinkit runs only through `AndroidBlinkitAdapter`; Rapido runs only through `AndroidRapidoAdapter`. The control plane sends one validated request over GCP SSH/IAP to a fixed worker command. The worker talks to Appium on localhost and Appium controls the persistent official provider apps. MCP never exposes selectors, coordinates, device commands, screenshots, UI XML, Appium sessions, phone numbers, OTPs, or emulator state.

Preparation selects the saved address, rebuilds the cart after any store change, selects exact COD, extracts exact terms, and stops before `Place Order`. Newly prepared grocery proposal hashes bind items, quantities, prices, unavailable items, fees, total, address, payment mode, ETA, expiry, and the provider fingerprint. Legacy snapshots remain readable, but Android dispatch requires the checkout fingerprint carried by a newly bound proposal. Commit binds the proposal ID, canonical proposal hash, provider fingerprint, idempotency key, and validity window. The worker persists `dispatching` before one exact final action. Any unverified post-dispatch outcome is `ambiguous`; reconciliation is read-only and never repeats the final action.

Provider interaction requires `ERRANDOS_LIVE_BROWSER_ACTIONS=true` for compatibility with the existing kill-switch name. Final ordering separately requires `ERRANDOS_LIVE_COMMIT=true`. Blinkit execution must be `android`; Playwright and provider API execution are rejected during deployment validation.

Rapido ride preparation binds pickup and drop-off references and summaries, the exact ride option, fare range, fees, pickup ETA, duration when available, payment mode, expiry, and provider fingerprint. Rapido final dispatch additionally requires `ERRANDOS_RAPIDO_LIVE_COMMIT=true`; it defaults false independently of the global gate. Chat confirmation is not an approval capability for Rapido. Immediately before dispatch, the worker re-reads the live terms, persists `dispatching`, and attempts the final request once. Any timeout or unverified confirmation is `ambiguous`; reconciliation reads recent trips and never requests another ride.

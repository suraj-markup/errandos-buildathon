## Global rules

1. Record the Git commit and whether the working tree is dirty. Live evidence
   from an uncommitted build must also record the installed APK SHA-256 and the
   exact server artifact identity.
2. Use one exact device serial. Multiple ADB transports for the same Pixel are
   acceptable only when every command pins the intended serial.
3. Verify the Pixel-to-server path before opening a shopping flow. For the
   current APK, which calls `127.0.0.1:3100`, evidence must contain an exact
   `tcp:3100 -> tcp:3100` ADB reverse mapping or a versioned APK whose endpoint
   is independently proven reachable.
4. Capture no screenshots or accessibility source from a sensitive screen.
   Reports contain semantic state, opaque identifiers, hashes, timings, and
   redacted errors—not addresses, phone numbers, OTPs, credentials, or raw UI
   trees.
5. Stop on a changed build, changed account, unexpected dialog, stale
   observation, ambiguous mutation, provider integrity warning, connectivity
   loss, duplicate action, or unverified state. Do not improvise around it.
6. H092 and H093 use different operation IDs, evidence files, authorization
   windows, and operator decisions. They are never one exploratory session.
7. A configured live-commit flag is only a technical gate. It is never human
   authorization.

## H092 — physical-Pixel shopping canary

### Entry gate

- The machine-enforced preflight emits exactly
  `RESULT h092_preflight=ALLOWED blocked=0` on the frozen release artifact.
  Human judgment, an earlier report, or an ordinary readiness result cannot
  override a refusal.
- Exact Pixel model/serial, Android version, awake/unlocked state, overlay
  package identity, permissions, foreground service, server HTTP 200, Appium
  ready state, and Pixel-to-server bridge are recorded.
- Blinkit authentication and saved location are verified without displaying
  private values in the report.
- `ERRANDOS_LIVE_COMMIT` is exactly false in the allowlisted server
  configuration and the final-dispatch source guard is structurally proven.
  H092 requires both; one no longer substitutes for the other.
- No Appium session from another test is active.
- The operator has approved the two named low-value products, maximum
  quantities, and restoration of the initial cart. This approval permits only
  the reversible H092 mutations, not an order.

### Execution evidence

1. Read the initial cart and record its exact lines, quantities, total,
   provider fingerprint, and observation time in redacted form.
2. Start one two-item task. Each item has a stable task item ID and desired
   absolute quantity.
3. Resolve item one through a spoken choice and item two through a card choice.
   Record the clarification ID, selected offer ID, task revision, and atomic
   acknowledgement for each. A late second response must be `duplicate` or
   `rejected` and must not enqueue.
4. For each item, record one operation ID, the before/after cart fingerprints,
   mutation boundary, reconciliation result, item-completion event, and next
   task step. No completed add may repeat on the checkout utterance.
5. Read the final cart and prove it contains exactly the approved desired
   state—no duplicate line and no additional quantity.
6. Produce a checkout review that is explicitly `NOT ORDERED`. Record exact
   items, quantities, fees, total, address label, payment availability, ETA,
   expiry, and provider fingerprint. Do not issue a final confirmation grant
   and do not call a final action.
7. Restore the initial cart exactly, then perform a read-only inspection.
   Cleanup is itself a bounded mutation and must be reported as ambiguous if
   not verified; it must never trigger checkout or order recovery.

### Pass gate

- Both choice channels resolve atomically; both items finish once; ordered
  progress is visible; checkout review is exact and says `NOT ORDERED`;
  initial and restored cart fingerprints match; final dispatch count is zero;
  false-success, duplicate mutation, ambiguity, and privacy counts are zero.
- Any missing evidence keeps H092 open. A readiness-only probe does not
  partially pass the physical shopping canary.

## H093 — separately authorized low-value COD canary

### Authorization gate

H093 starts only after H092 passes and the owner provides a new, time-bounded
authorization naming the provider, product/quantity ceiling, delivery-address
label, COD requirement, maximum all-in total, and canary window. The rollout
operator records an authorization ID without copying private conversation
content.

Preparation then yields an immutable proposal. The owner must receive its exact
items, quantities, prices, unavailable items, fees, total, address label,
payment mode, ETA, expiry, proposal ID, proposal hash, and provider
fingerprint. A second exact COD confirmation bound to that proposal, task
revision, owner, client, and action digest is required. “Yes,” an add-to-cart
statement, prior H092 approval, or `ERRANDOS_LIVE_COMMIT=true` is insufficient.

### Dispatch gate

- One operator, one proposal, one unexpired confirmation grant, one
  idempotency key, one operation, and one final-action reservation exist.
- Re-read exact provider terms immediately before dispatch. Any change
  invalidates the proposal and requires a fresh review and confirmation.
- Invoke the unique final action at most once. A timeout/disconnect after the
  mutation boundary becomes permanently ambiguous and goes only to read-only
  reconciliation. It is never retried.
- Success requires a verified provider receipt/reference bound to the exact
  proposal. UI disappearance, model prose, or a non-unique history match is not
  success.

### Pass gate

- Exact confirmation was consumed once; provider dispatch count is one;
  duplicate dispatch count is zero; a verified receipt/reference exists; a
  read-only reconciliation returns the same unique order; and no unrelated
  cart, checkout, or order action occurred.
- After evidence capture, return the live-commit gate to its normal disabled
  state. Preserve transaction records for audit.

The present evidence task is not H093 authorization and must not dispatch an
order.

## Rollback gates

| Trigger | Immediate action | Required evidence before resuming |
| --- | --- | --- |
| Duplicate mutation, repeated final action, false success, or confirmation bypass | Disable live commit and Realtime phone tools; stop mutations. | Operation ledger, idempotency record, exact before/after observations, read-only reconciliation, root cause, and a regression test. |
| Ambiguous cart mutation | Stop the task at `needs_reconciliation`; do not retry. | Fresh read-only cart inspection proves desired, unchanged, or divergent state. |
| Ambiguous final dispatch | Preserve `ambiguous`; never replay final action. | Unique read-only order-history/receipt match or explicit unresolved result. |
| Sensitive capture or package-scope escape | Disable the affected general-mobile adapter and screenshot/vision control. | Redacted incident record, privacy regression, package-scope test, and fresh supervised cohort. |
| Stale observation or no-progress loop | Cancel model output and stop adapter work at the safe boundary. | Fresh observation, bounded recovery result, and no mutation during the stale window. |
| Realtime latency/failure/safety regression | Fall back to bounded Responses; Sarvam and authoritative task state remain. | Versioned cohort report meeting quality, latency, fallback, replay, and cancellation gates. |
| Pixel/backend reachability loss | Stop before any new mutation. | Exact device, bridge, server, Appium, and build-identity preflight rerun. |

Rollback is deployment/configuration work performed by an authorized release
operator. The read-only readiness script only detects blockers; it never
changes a flag, process, bridge, adapter, or device.

### Offline fail-closed evaluator

`pnpm release:offline:check` is the release gate. It must exit nonzero while

missing. Never weaken or bypass a blocker to obtain a green command.
